# BoolODE Stage 2 Simulation

Use this skill when Stage 2 needs a controlled simulation because the registered
real benchmark catalog cannot observe the mechanism claimed by the approved
algorithm proposal.

Prefer real benchmark data whenever it can evaluate the approved claim metric
fairly. Do not create a simulation merely because W1/TMV is hard. A simulation
is justified only when the claim needs an observable mechanism that the real
catalog does not contain or cannot label. The simulation must test a meaningful
claim metric tied to the approved proposal, and it must be frozen so
builtin/reference baselines can run on the same data.

## Available Generator

DynBench lives under `benchmark/dynbench/`.

- `benchmark/dynbench/simulators/boolode_sim.py`: Hill-function ODE/SDE
  simulator with growth, snapshots, and ground-truth velocity, growth, fate,
  perturbation, and GRN.
- `benchmark/dynbench/simulators/scenario_factory.py`: config-driven generator
  for task packages and ground truth.
- `benchmark/dynbench/simulators/test_configs/`: reusable scenario configs.
- `benchmark/dynbench/eval/dynbench_eval_v2.py`: six-metric evaluator.

## Modeling Principle

BoolODE-style simulations generate single-cell snapshots from a known gene
regulatory dynamical system. The hidden continuous-time state is a gene
expression vector `x(t)`. Each gene follows a stochastic ODE:

```text
dx_i = [production_i * Hill(regulators of i) - degradation_i * x_i] dt
       + sigma dW_i
```

Positive edges use activation Hill functions, negative edges use repression
Hill functions. The scenario factory builds a GRN with transcription-factor
toggle modules, reporter genes, optional late confounders, and optional noise
genes. Cells are simulated forward, sampled into discrete time bins, and saved
as `train.h5ad` with the CytoBridge training contract.

Growth is optional but important for unbalanced algorithms. It is generated by
a gene-dependent birth/death wrapper:

```text
growth_rate(cell) = base_rate + amplitude * sigmoid(beta * (growth_gene - threshold))
```

The generated ground truth may include velocity, growth, fate labels,
perturbation effects, and GRN structure. Use those labels only for evaluation
or claim metrics. Do not expose hidden labels to the training loss unless the
approved proposal explicitly allows that supervision.

This setup is useful when the claim is mechanistic: fate branching, growth
driver recovery, robustness to confounders, topology/interaction recovery, or
trajectory prediction through held-out time bins. It is not a replacement for
real biological evidence when real data can test the claim directly.

## Minimal Workflow

1. State why existing benchmark datasets cannot test the claim.
2. Choose or write a scenario config that isolates the mechanism.
3. Prefer `generate_and_register_stage2_simulation_dataset(...)`. It generates
   the scenario, freezes the generator/config, registers the generated
   `train.h5ad`, and returns `dataset_config_overrides` for
   `run_campaign_trial(...)`. For DynBench/BoolODE output, the tool also adds
   the CytoBridge benchmark contract fields when needed:
   `obs['time_point_processed']` and `obsm['X_latent']`.
4. Inspect the generated task package and ground truth.
5. If you use custom code instead of the tool, register the generated
   `train.h5ad` with `register_stage2_simulation_dataset(...)`, not plain
   dataset registration.
6. Record the generator path, config path, generated output path, and
   `simulation_version` in campaign/proposal notes.
7. Run the custom algorithm and comparable builtin/reference baselines on the
   same frozen dataset version.

Example with the closed-loop tool:

```python
generate_and_register_stage2_simulation_dataset(
    dataset_id="<algorithm_id>_stage2_claim_sim",
    scenario_config_path="benchmark/dynbench/simulators/test_configs/compact_toggle_high_noise.json",
    output_id="<algorithm_id>_stage2_claim_sim_v1",
    algorithm_id="<algorithm_id>",
    proposal_id="<proposal_id>",
    simulation_version="<algorithm_id>_stage2_claim_sim_v1",
    claim_metric_name="<claim_metric_name>",
    notes="Use only because the real benchmark catalog cannot label the approved claim mechanism.",
)
```

The returned `dataset_config_overrides` can be passed directly to
`run_campaign_trial(...)` for the Stage 2 panel.

Fallback with `execute_python`:

```python
from pathlib import Path
import runpy
import sys

repo = Path.cwd()
script = repo / "benchmark/dynbench/simulators/scenario_factory.py"
config = repo / "benchmark/dynbench/simulators/test_configs/compact_toggle_high_noise.json"
output_dir = Path.home() / ".cellcompass/generated_simulations/<simulation_id>"

old_argv = list(sys.argv)
try:
    sys.argv = [
        str(script),
        "--config", str(config),
        "--output-dir", str(output_dir),
        "--quiet",
    ]
    runpy.run_path(str(script), run_name="__main__")
finally:
    sys.argv = old_argv

print(f"Generated BoolODE simulation under: {output_dir}")
```

The generated directory should contain a task package with `train.h5ad` and
ground-truth metadata. Use the task package for training and the ground truth
only for evaluation/claim metrics, never for training-time leakage.

BoolODE is optional. If the approved claim requires a different synthetic
mechanism, write a small custom generator instead, or copy and adapt the
DynBench code paths above. The output still needs the CytoBridge training
contract, especially `obs['time_point_processed']` and `obsm['X_latent']`, and
the frozen generator must be registered with
`register_stage2_simulation_dataset(...)`.

## Config Guidance

Prefer config-driven scenarios over ad hoc code edits. A useful Stage 2
simulation has:

- a clear positive mechanism where the approved algorithm should help;
- a claim-absent, shuffled, random, or degenerate control when possible;
- confounders that defeat trivial heuristics if the claim is about mechanism
  recovery;
- a frozen seed and config file;
- explicit observable metrics from rollout artifacts.

The claim metric should fail when the model collapses, ignores the claimed
mechanism, uses shuffled side information, or only fits marginal distribution.

## Scenario Parameters

A scenario config is a JSON object, or a list of objects. Start from
`benchmark/dynbench/simulators/test_configs/*.json` and edit only the fields
needed to test the approved claim.

Core identity fields:

- `name`: short semantic name used in reports.
- `scenario_name`: optional exact output directory under `task_packages/`.
- `seed`: random seed. Freeze it before trusted Stage 2 evidence.
- `notes`: free-text rationale for the scenario.

Topology fields:

- `topology`: one of `procedural`, `toggle_switch_3gene`, or `llm_spec`.
- `topology_spec.topology_family`: supported families include
  `branching_tree`, `compact_toggle`, `branching_with_feedback`,
  `competitive_multistable`, and `asymmetric_tree`.
- `topology_spec.feedback_strength`: adds reporter-to-TF feedback for feedback
  or competitive families.
- `topology_spec.cross_branch_coupling`: adds coupling or competition between
  branch TFs.
- `topology_spec.asymmetry_strength`: makes branch reporter strengths unequal.
- `topology_spec.density_bias`: `low`, `medium`, or `high`; higher values add
  denser reporter/regulator links in supported families.

Size and difficulty fields:

- `n_fates`: number of terminal fates, usually 2, 4, 8, or 16.
- `n_reporters_per_tf`: reporter genes per transcription factor.
- `n_confounders`: late marker genes that can correlate with time but should
  not define the true mechanism.
- `n_noise_genes`: uncorrelated nuisance genes.
- `n_init_cells`: starting cell count before growth/death simulation.
- `n_time_bins`: number of sampled snapshot bins.
- `holdout_bins`: time bins omitted from training/evaluation targets as
  configured by the task package.
- `t_end`: continuous simulation end time.

Dynamics fields:

- `growth_type`: `single`, `multi`, or `interaction`. Use `single` for a
  simple growth driver, `multi` for multiple fate-specific growth effects, and
  `interaction` when the claim concerns coupled growth/dynamics.
- `noise_sigma`: SDE noise scale. Increase it to test robustness; do not
  increase it just to make every method fail.

Practical interpretation:

- More fates, more time bins, higher noise, denser topology, more confounders,
  and interaction growth make the task harder.
- If the claim metric is about mass or growth, vary `growth_type` and include a
  claim-absent control with weaker or disabled growth.
- If the claim metric is about topology or interactions, vary
  `topology_spec.*` and include shuffled/ablated side information controls.
- If a real registered dataset can already evaluate the claim, use the real
  dataset first and keep the simulation as a supplementary controlled check.

## Safety Rules

- Do not train on hidden ground-truth velocity, growth, fate, perturbation, or
  GRN labels unless the proposal explicitly allows that supervision.
- Do not edit generated ground truth after registration.
- Do not use DynBench scores as a substitute for real biological evidence when
  the approved proposal is biology-first and suitable real data exists.
- Do not make the campaign stage panel simulation-only unless the proposal or
  claim truly requires a controlled synthetic mechanism test.

## Useful Checks

After generation, verify:

```python
from pathlib import Path

output_dir = Path.home() / ".cellcompass/generated_simulations/<simulation_id>"
for path in sorted(output_dir.rglob("*")):
    if path.is_file():
        print(path)
```

If a scenario requires custom topology beyond existing configs, modify a copy of
an existing JSON config under a new name and keep that file under version
control or in the frozen simulation artifact directory.
